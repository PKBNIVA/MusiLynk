# SEO and performance audit, October 2026

Audited 2026-10-01 against the live site (https://verse-music-platform.vercel.app, API on Railway) at commit `7508dce`
(production). Read-only requests only, at most one per second. The raw Lighthouse JSON for the live runs is kept outside the
repo in `/home/user/seo-perf/`; the numbers below are copied from it.

## Summary

- Accessibility and best-practices are 100 on every page. SEO is 100 everywhere except the hire and rates pages, which
  score 69 because the API currently marks them `indexable: false` (too few organic profiles) and the page adds
  `noindex`. That is intended behaviour, not a defect.
- Performance is the weak spot, and it is almost entirely JavaScript boot time. Mobile mean is 62 and desktop mean is
  85. LCP is 4.3 to 6.6 s on mobile (simulated slow 4G, 4x CPU). The pages are client-rendered: the HTML is an empty
  `<div id="root">`, so the LCP element (a hero photo or the `<h1>`) only exists after the entry script, the route
  chunk and, for data pages, an API call have run. No non-UI change can remove that; see the handoffs.
- SEO plumbing is mostly sound (per-route prerendered heads, per-share OG images, sitemap limited to organic records,
  noindex on thin pages). The real defects were: the fallback HTML for every dynamic URL carried the home page's
  canonical and title; unknown URLs and missing assets returned `200` (soft 404, and a missing `/assets/*.js` was
  cached as `immutable` for a year); Googlebot was not routed to the share pages for acts and portfolios; and the
  JobPosting JSON-LD could contain invalid `unitText` values.
- API: nothing is over 500 ms p95 except two cold-cache cases (talent list 591 ms, popular searches 946 ms on its
  first request). The talent list had an N+1 (95 queries for 24 people); fixed here.

Over 500 ms p95: the talent list (591) and the popular-searches endpoint (946, only its first, cache-missing
request; the next nine were 223 to 292 ms). The share-page 523 ms is one outlier among 10.

Causes, from `EXPLAIN` and per-request SQL logs on a local database seeded with `bin/rails demo:showcase`
(110 musicians, 40 hirers; database `verse_seo_seed`):

- **Talent list: N+1 on verified people.** `public_profile` called `Verification::Tier.for` (two COUNTs: urgent
  requests filled, completed bookings of owned acts) and `verification_summary` (one query) per row, on top of the
  batched `ProfileStats`. 95 queries per page, 285 ms warm locally. Now batched: **16 queries**, 102 ms warm.
- **Cold cache cost of hire data.** `popular-searches` runs one ILIKE-scan COUNT per role x city (192) and used
  `counts_for`, which adds two more queries; the sitemap does the same for 192 organic counts, plus 192 rate
  lookups. All cached for 1 h, so only the request after expiry pays (and, without a lock, so does every concurrent
  request). Now one COUNT per combination and `race_condition_ttl: 30.seconds` so a single request recomputes.
  Sitemap queries 389 to 153; hire page 57 to 10.
- **Missing index.** `urgent_requests.filled_by_id` was unindexed; `Tier` filters `status = 'filled' AND filled_by_id IN (...)`.
  With 300,000 urgent requests (100,000 filled): before, a bitmap scan of the whole `status` index plus 6,609 heap
  buffers, **41.0 ms**; after the partial index, an index-only scan, 75 buffers, **0.12 ms**.
- Payload: the talent and jobs lists are about 39 kB each uncompressed for 24 rows (gzip is on). Trimming the public
  card fields would help mobile; not done because the pages consume those fields.
- `/api/public/*` responses send `Cache-Control: max-age=0, private, must-revalidate`, so the browser revalidates every
  navigation. Left alone: a 30 s public TTL would show stale profiles to someone who just edited theirs.

## 5. Handoffs for page components (not edited here)

Files are under `src/app/`. Line numbers are at commit `7508dce`.

1. **Make the LCP element exist before JavaScript finishes.** The only route to LCP under about 3 s on mobile is HTML that
   already contains the hero. Options, in order of effort: (a) render the hero/`<h1>` of `/`, `/pricing`, `/guide`,
   `/urgent`, `/hire/*`, `/rates/*` into the static shell at build time (the prerender script can inject it once the
   components expose a static variant); (b) at least avoid the empty "Preparing your Verse workspace" splash for public
   routes so the first paint is the page chrome. Photo preload and API preconnect were tried and do not change LCP on
   their own (section 1).
2. **Boot cost.** `react-vendor` is 76 kB gzip and costs 1.1 to 1.8 s of mobile main-thread time; the long tasks on
   `/opportunities/:id` (650 ms + 450 ms) and `/professionals/:id` (940 ms) are React rendering the full page tree plus
   `components/PageMeta.tsx`'s effect. Check what `pages/public/PublicOpportunity.tsx` and `PublicProfile.tsx` render
   eagerly (the opportunity page also fetches `/api/jobs?limit=24` for similar jobs, which could wait until idle)
   and split any dialog or editor code out of the first render. 32 to 56 kB of unused JS per page.
3. **Layout shift.** `pages/public/PublicTalent.tsx:102` (`<form role="search">`, CLS 0.049 mobile): content above or
   below the form changes height when the result count and cards arrive; reserve the count line and a skeleton grid
   with fixed height. `pages/Pricing.tsx:191` (`data-testid="pricing-plans"`, CLS 0.025): the plan grid appears after
   the plans response; render a fixed-height skeleton.
4. **Home weight.** `components/landing/RoleTiles.tsx` and `HowItWorks.tsx` load 14 further 800 px photos (about
   490 kB) at low priority within the first 4 s; consider `content-visibility: auto` on the tile section or fewer
   eager-adjacent tiles. Accessibility was 100 everywhere, and no image lacks dimensions, so no alt-text or sizing fix
   is needed.
5. **`pages/public/PublicOpportunity.tsx:49-66` (client JobPosting).** Mirror the server fix: map
   `compensation_period` to HOUR/DAY/WEEK/MONTH/YEAR or omit `baseSalary` (it currently uppercases `session`, `show`
   and `project`); add `applicantLocationRequirements: { '@type': 'Country', name: 'IN' }` when `workplace ===
   'remote'`; do not emit `minValue`/`maxValue` when `null`.
6. **`pages/public/HirePage.tsx:76-82` (BreadcrumbList).** `item` must be an absolute URL (`${origin}/`,
   `${origin}/music-professionals`, ...). The build-time version in `prerender-heads.mjs` already is, but the
   client copy replaces it on hydration with the relative ones. `RatesPage.tsx` has no BreadcrumbList; add the same.
7. **Thin hire/rates pages are indexable in the static HTML.** The page adds `noindex` only after its API call. If
   you want that decided server-side, the prerender could fetch each page's `indexable` flag at build time
   (`/api/public/hire-pages/:role/:city`), at the cost of a build that depends on the API and goes stale until the
   next deploy. Left as is because the sitemap already excludes them and Google runs the script.
